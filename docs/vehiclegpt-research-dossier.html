VehicleGPT Research Dossier

How to build an on-device language assistant that reads a software-defined vehicle's CAN, SOME/IP, VHAL, QNX, ADAS and diagnostic data and answers questions about it in under 2 seconds, offline, inside 2 GB of RAM. This page covers what already exists worldwide, what the evidence says, and the architecture it points to.

Example questions from the brief, which the design must answer: Why has my driving range reduced over the last two weeks? When did fuel efficiency show the largest drop? Show all ADAS disengagement events from yesterday. What happened before the battery overheating warning? Compare energy consumption between city and highway driving.

Core design idea

The language model routes; deterministic code computes. A 0.5–1B model on two small cores is slow to read prompts and unreliable at arithmetic. So it only turns a question into a short, grammar-checked tool call. Precomputed analytics and SQL produce the numbers, and a template writes the answer. Accuracy then comes from the data layer, not the model.

  1. L0 deterministic router. An intent and slot matcher plus a time-phrase parser ("last two weeks", "yesterday") answers common questions in under 100 ms without calling the model. This is the most reliable way to meet the 2 s requirement for common queries.
  2. L1 small-model tool caller. Handles long-tail and compound questions. The system prompt and tool definitions are KV-cached once, so each query prefills only about 30 new tokens. The output is a GBNF-constrained JSON tool call of about 10–15 tokens.
  3. Deterministic tools. About 12 validated functions over the store return value, unit, period, evidence and chart data.
  4. Grounded composer. Per-intent templates, plus an optional one-sentence explanation from the model. The sentence is dropped if it contains a number not present in the evidence (the CarExpert moderator idea).

Why not let the model write SQL?

Sub-2B models reach only 56.9% (0.5B) and 67.1% (1.5B) execution accuracy on the BIRD text-to-SQL benchmark, even after fine-tuning and RL (SLM-SQL). Constrained tools are auditable and testable. Separately, time-series QA research finds that agents querying data through tools beat feeding raw numbers to the model by up to 10 points (arXiv 2606.16545).

Closest production precedent

Mercedes-Benz R&D (arXiv 2501.02342) pruned Phi-3-mini from 3.8B to 1.8B parameters, quantized it to 4-bit GGUF and ran it in llama.cpp on a 7-core ARM head-unit CPU at about 11 tokens/s. Its function-call exact-match accuracy was 0.86, against 0.75 for their production speech system. They trained on 25,000 synthetic examples plus 500 refusals, using Octopus-style functional tokens. Isolation boundary

A hypervisor (QNX Hypervisor 8.0 for Safety, Xen or Gunyah) partitions CPU, memory and, through bandwidth regulation, cache and DRAM contention. The AI has no write path to any bus.

One data model

Every protocol is normalised to COVESA VSS paths such as Vehicle.Powertrain.Range and Vehicle.Speed. Tools, prompts and the catalog all speak VSS, so a new vehicle line only needs a new mapping file.

The data layer is Eclipse Kuksa Databroker, a Rust gRPC server holding the VSS tree. Providers write into it and the AI only reads. The Eclipse SDV CarMate blueprint already wires CARLA → Kuksa → a local LLM through Ollama, which makes it the closest open reference.

Runtime

  • llama.cpp as baseline: GGUF, GBNF grammars, prompt cache, NEON. This is what Mercedes-Benz shipped on.
  • MNN-LLM as challenger: claims 8.6× prefill and 2.3× decode over llama.cpp on phone CPUs (arXiv 2506.10443) Vendor claim
  • Vendor NPU SDKs (QNN, eIQ, TIDL, RKLLM) via ONNX or ExecuTorch where the SoC has one.

Fine-tuning recipe

  • 10–25k synthetic question → tool-call pairs, generated by a large model from the tool schemas and the VSS catalog.
  • Around 500 refusal examples, plus paraphrases in Indian and global English.
  • LoRA fine-tune, then export to GGUF Q4/Q8.
  • Optional functional tokens for each tool (Octopus v2 / Mercedes approach) to shorten output.

EmbeddingGemma 2 (new, Apache-2.0)

  • The 270M text part does semantic intent matching for L0 and ToolRAG for L1.
  • RAG over the owner's manual and DTC descriptions.
  • The vision encoder (170M) embeds ADAS keyframes, so camera events become searchable without storing video.
  • Matryoshka 256-d vectors keep about 99% of 768-d quality. Use bf16 or fp32, never fp16. On-CPU latency is To verify.

Reference points: an RK3588 runs Qwen2.5-1.5B Q4 at 22.6 tok/s with llama.cpp on its A76 cores, and four threads beat eight because the A55 cores hold the pipeline back (Turing Pi). On an RK3566 (4× A55), a 3B model ran at 2.62 tok/s, and the author found scaling bandwidth-bound (TaqaBuddy). That puts a 0.5B model on A55 cores in roughly the low-teens tok/s, which is an extrapolation to measure.

Historical storage

Weeks of history on embedded flash, without a heavyweight database.

TierContentRetentionTechnology
HotAll subscribed signals at full rate2–5 min ring bufferIn-RAM ring (~64 MB)
Event capturePre- and post-window around each warning, DTC or ADAS eventKept with the eventprecontext table
Warm1 Hz or on-change samples, 1 min and 1 h rollups, events, DTCs, trips, daily features4–8 weeksSQLite WAL, WITHOUT ROWID (sig_id, ts)
ColdCompressed daily partitionsMonths (optional)Parquet or zstd segments
  • Recorder in Rust or C++. Each signal has a policy: on-change with deadband for slow signals, 1 Hz for dynamics. Appends are batched so flash write amplification stays low.
  • Sizing target: about 20–60 MB/day for 200–500 signals To verify. Six weeks then fits in a few GB of eMMC.
  • Why SQLite: proven in automotive, no server process, small RAM footprint. DuckDB is fine for analytics on Parquet, but it has no retention engine (InfluxData comparison).
  • Protection: fscrypt or dm-crypt with keys in the SoC HSM/TEE, retention purge, and a wipe on ownership transfer.

Trends, anomalies and causes

The evaluation asks the system to explain causes. That is done before anyone asks, so queries stay fast.

Expected-consumption baseline

A physics-plus-regression model predicts Wh/km (or L/100 km) from speed, acceleration, grade, ambient temperature, HVAC load, tyre pressure and battery state of health. The residual is attributed to factors, e.g. "range down 18%: 9% cold and heater, 5% tyre pressure, 4% more highway". Winter thermal loads alone can cut EV range by over 20% (preprint).

Change and anomaly detection

Changepoints on daily features with ruptures (BSD-2, 2.1k stars). Rolling median/MAD z-scores per subsystem, message-gap detection and physical plausibility rules (the approach in autodiag-copilot). DTC co-occurrence.

Event timelines

For each warning: which signals deviated first, in onset order, inside the captured pre-window. For example: coolant pump current drops, cell ΔT rises, then the over-temperature DTC.

User interaction design

Driver

Voice or text in the IVI. Offline ASR (whisper.cpp or the vendor's engine) feeds the same /ask API. The answer is short and spoken, with a card and a mini chart on screen. No numbers appear that the evidence does not contain.

Service engineer

An authenticated SOVD-style REST API and web console: DTC timelines, event pre-context plots, raw evidence export. This mirrors Sibros' SOVD-based AI Concierge.

Fleet and validation

Batch queries, scenario reports and anomaly digests, exported on opt-in sync. The cloud is optional and never required to answer.

Safety, security and privacy

  • Freedom from interference (ISO 26262). The AI is QM software in its own hypervisor guest, with pinned CPUs, a memory cap and memory-bandwidth regulation. A hypervisor alone does not stop cache or DRAM contention (Promwad). A watchdog restarts it, and if it fails, no vehicle function changes.
  • No actuation. The AI gets a read-only, one-way data feed and has no write path to CAN, SOME/IP or VHAL. Peykan's opt-in tiers and frame allowlist are a useful pattern for the service-tool side.
  • Cybersecurity. ISO 21434 TARA, UNECE R155 CSMS, secure boot, signed containers and model OTA (R156, Uptane-style), and mutually authenticated service sessions.
  • Privacy. Local-only processing, data minimisation, coarse GPS, role separation, consent and delete controls (GDPR, India DPDP Act 2023). Camera data stays as metadata and embeddings, never raw video.

Simulation and validation

Scenario engine with ground truth

YAML scenarios drive a vehicle model and emit through the real protocols (CAN via DBC on vcan, SOME/IP, DLT, DTCs, ADAS events). Each scenario records when its faults start, which gives exact expected answers for evaluation. Scenarios: range loss over weeks, an efficiency-drop day, a battery overheating sequence, ADAS disengagements, a city/highway mix.

CARLA

Driving dynamics and ADAS situations. Yes, CARLA CAN puts DBC-defined frames on vcan0. CarMate feeds Kuksa from CARLA. TEASER generates realistic CAN from CARLA runs.

Recorded data

  • VED: 383 cars, a year of OBD fuel and energy trips, Apache-2.0. eVED adds map attributes.
  • comma2k19: raw CAN plus decoded speed and steering, 2019 one-minute segments, about 100 GB, MIT.
  • ROAD and HCRL: CAN with attacks.

Evaluation set

About 300 queries: the five brief types, paraphrases, ambiguous and unanswerable questions. Metrics: L0 hit rate, tool exact match, numeric accuracy, hallucination rate, p50/p95 latency per stage, peak RSS, storage per day.
